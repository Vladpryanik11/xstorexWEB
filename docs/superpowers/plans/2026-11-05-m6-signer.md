# M6 Signer Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On `/signer` a user whose plan includes the `signer` option uploads their own IPA, signs it with the Xstore certificate of their device's account or with their own `.p12` + `.mobileprovision`, optionally under another bundle id and name, and installs it like a catalog app.

**Architecture:**
- Reuses M1 resumable uploads and `ipa:inspect` (purpose `signer`, private `uploads` bucket), M4 signing, SSE and install tokens.
- API `signer` module: uploads within the plan limit, user certificates validated in memory and stored encrypted, signing requests with options.
- Worker: the signing job learns a `user_upload` kind and the `user` certificate source; a daily job deletes expired uploads and their builds.

**Tech Stack:** M5 stack. `node-forge` (PKCS#12 parsing in the API for validation), Nest `FileFieldsInterceptor` (multer memory storage) for certificate files.

**Spec:** `docs/superpowers/specs/2026-11-02-xstore-design.md` — §3.1 (`signing` «своя подпись пользователя»), §4.5, §5 (`UserUpload`, `UserCertificate`, `SigningJob`, `Plan.features.signer/uploadLimitMb`, `Enc` rule), §6.3 (`/signer`, `/devices` «Подписать свой IPA»), §7 → M6. Builds on M1 (uploads, inspect), M3 (secrets, `parseMobileProvision`), M4 (signing, tokens), M5 (`deviceFeatures`).

## Owner decisions this plan depends on

1. **Validation of a user certificate happens in the API, in memory, before encryption.** The API never decrypts a stored secret; only the worker does (spec §5 rule holds).
2. **Profiles without a device list** (`ProvisionsAllDevices`, enterprise) are refused: the spec requires checking the UDID in the profile.
3. **Signer builds are private and not cached across users.** They live in the `uploads` bucket and expire together with the upload (`signer.uploadRetentionDays`, default 7).
4. **Icons of user IPAs are private too:** stored in the `uploads` bucket and served through 15-minute links.
5. **The upload limit comes from the device's active plan** (`uploadLimitMb`); with several devices the best active plan among the user's devices counts.

## Global Constraints

- All M0–M5 Global Constraints hold.
- `/signer` and every signer endpoint require the `signer` feature on at least one active device right of the user (`FEATURE_REQUIRED` otherwise).
- File limits: IPA ≤ `uploadLimitMb` MiB; `.p12` ≤ 50 KB; `.mobileprovision` ≤ 1 MB.
- Rate limits: 20 IPA uploads per day per user; 10 certificate uploads per day per user; 30 signing requests per hour per user.
- Custom bundle id: `^[A-Za-z0-9-]+(\.[A-Za-z0-9-]+)+$`, ≤ 155 chars. Custom name: 1–50 chars, Unicode allowed, no control characters.
- Storage keys: originals `signer/<userId>/<uploadId>/original.ipa`, icons `signer/<userId>/<uploadId>/icon-{57,512}.png`, builds `signer/<userId>/<uploadId>/<signingJobId>.ipa`, all in `<prefix>uploads`.
- `UserCertificate.p12Enc` and `passwordEnc` join the `secrets:rotate` table list.

## Review Focus

1. **Wrong `.p12` password:** `CERT_INVALID` «Не удалось открыть сертификат: проверьте файл и пароль», nothing stored, the password never logged → Task 2 test `wrong password stores nothing`.
2. **Profile without this device:** signing with it is refused with `UDID_NOT_IN_PROFILE` «Этого устройства нет в профиле» before any job starts → Task 3 int test `udid must be in the profile`.
3. **Too large or no `signer` option:** refused before the upload starts, with the limit in the message → Task 1 int tests `limit from the plan`, `no signer option`.
4. **Odd options** (bundle id with spaces or Cyrillic; name «Мой Telegram 🚀»): the bundle id is refused, the name is accepted and shows correctly in the manifest and on the home screen → Task 3 tests `validates bundle id`, `keeps a Unicode name`.
5. **An old install link to an expired upload:** 410 `INSTALL_LINK_EXPIRED`, never a broken download → Task 4 int test `expired upload link`.

  - Worker: on `ready` for `signer` → `UserUpload` with `expiresAt = now + signer.uploadRetentionDays`; `encrypted` → upload `rejected` with `IPA_ENCRYPTED` and the original deleted.

  - `POST /install/jobs/:id/token` for a signer job issues an `InstallToken` with `buildKey`, title = `displayName ?? upload.name`, bundle id = option or original, icons from private keys (presigned in the manifest).

**Interfaces:**
- Produces:
  - Job `maintenance:purgeSigner` (daily 04:00 Europe/Moscow): uploads past `expiresAt` → delete the original, icons and every build under `signer/<userId>/<uploadId>/`; `IpaUpload` → `expired`; `UserUpload` kept for history with `expiresAt`.   - User deletes (`DELETE /signer/uploads/:id`, `DELETE /signer/certificates/:id`) remove objects immediately.
