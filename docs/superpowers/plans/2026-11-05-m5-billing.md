# M5 Billing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A user picks a plan on `/pricing`, pays through Platega, and the paid order turns into dated rights on the device: the device is registered with Apple at the plan's tier, paid addon apps unlock, renewals stack, and the admin manages plans, orders, refunds and manual grants.

**Architecture:**
- API `billing` module: plans, orders, a `PaymentProvider` interface with a Platega implementation and a fake one for development and tests, an idempotent webhook that confirms every payment through the provider API before applying it.
- Pure entitlement math lives in `@xstore/shared` so API, worker and web agree on dates and features.
- Worker `billing` queue: reconcile stuck orders every 5 minutes, expire unpaid orders, expire rights and send reminders.

**Tech Stack:** M4 stack. No Platega SDK: a small `fetch` adapter.

**Spec:** `docs/superpowers/specs/2026-11-02-xstore-design.md` — §2 («Оплата»), §3.1 (`billing`), §4.2 steps 1–3, §4.6 step 3 (`warrantyDays`), §5 («Оплата» and the rules: rights per device, `accessLevel = addon:<Plan.code>`), §6.3 (`/pricing`, `/checkout/[orderId]`, `/devices` «Продлить», `/profile` orders, admin «тарифы, заказы, возвраты», manual rights), §7 (webhook checks, 5-minute reconciliation), §9 (webhook unit test, e2e purchase through a Platega mock) → M5. Builds on M3 (`registerDevice`, migration) and M4 (`canInstall`).

## Owner decisions this plan depends on

1. **Platega API details.** Its documentation is not reachable from the planning session. Task 3 starts with the owner's merchant documentation; the values below (endpoints, `X-MerchantId`/`X-Secret` headers, `CONFIRMED`/`CANCELED` statuses) come from a third-party SDK and must be confirmed. Whatever the webhook authentication turns out to be, the plan never trusts the webhook body alone: it re-reads the payment from the Platega API before granting anything.
2. **Prices are whole rubles** (`priceRub Int`), set by the admin. No plan is seeded with a price.
3. **Refunds are made in the Platega cabinet.** «Отметить возврат» in the admin closes the order and ends its rights; it does not move money.
4. **One device plan per order**, plus any addons. An addon needs an active device right or a device plan in the same order.
5. **Device plan changes tier** (standard → reliable): after payment the device is re-registered on an account of the new tier.
6. **Warranty** counts from the start of the latest paid device right: `startsAt + warrantyDays ≥ now`.

## Global Constraints

- All M0–M4 Global Constraints hold.
- Currency: `RUB` only. Amounts are integers in rubles end to end.
- Order lifetime: unpaid orders expire after 24 hours. Reconciliation: every 5 minutes for orders `pending` longer than 10 minutes.
- Webhook endpoints: `POST /api/v1/billing/webhooks/platega` (and `/fake` outside production), raw body ≤ 64 KB, exempt from the Origin check (M1), never behind a session.
- `PAYMENT_PROVIDER=platega|fake`; `fake` is refused when `NODE_ENV=production`. Platega env: `PLATEGA_BASE_URL`, `PLATEGA_MERCHANT_ID`, `PLATEGA_SECRET`, optional `PLATEGA_PAYMENT_METHOD`. They are secrets: env only, redacted in logs.
- Rights chain keys: `device` for every device plan, `addon:<code>` for each addon.
- Reminders: email 7 days and 1 day before a device right ends.

## Review Focus

1. **Duplicate or replayed webhook:** the second delivery is acknowledged and changes nothing → Task 4 int test `replay is a no-op`.
2. **Amount or currency mismatch** (webhook or API says 1 ₽ for a 990 ₽ order, or `USD`): order not paid, critical alert → Task 4 int test `mismatch never pays`.
3. **Webhook never arrives:** the reconcile job pays the order within one run → Task 5 int test `reconcile pays a lost webhook`.
4. **Renewal before expiry:** the new period starts when the old one ends, not today → Task 2 test `stacks renewals`.
5. **Payment confirmed for an expired or refunded order:** no rights; an alert asks the admin to resolve it → Task 4 int test `late payment for a closed order`.

### Task 2: Entitlement math and the final rights rule

**Files:**
- Create: `packages/shared/src/entitlements.ts`

**Interfaces:**
- Produces:

  - `nextWindow(existing: EntitlementLike[], plan: { kind; code; durationDays }, at: Date): { startsAt: Date; expiresAt: Date }` — `startsAt = max(at, latest expiresAt in the same chain among non-revoked rights)`, `expiresAt = startsAt + durationDays` (whole days, UTC).
  - `activeRights(rights: EntitlementLike[], now: Date): EntitlementLike[]` — `startsAt ≤ now < expiresAt`, not revoked.
  - `deviceFeatures(rights, plans: Map<string, PlanFeatures>, now): PlanFeatures` — max over active device rights (`signer` OR, limits max).
  - `warrantyEligible(rights, plans, now): boolean` (owner decision 6).

  - `canInstall` rule from now on: device `active`; an active `device` right; `accessLevel` `free`, or `addon:<code>` with an active `addon:<code>` right; app/version rules unchanged.
  - `EntitlementLike` gains `startsAt` and `revokedAt?`.

### Task 4: Orders, webhook and applying a payment

**Files:**

- Test: `apps/api/test/orders.int.test.ts`, `apps/api/test/webhooks.int.test.ts`

**Interfaces:**
- Produces:
  - `GET /billing/plans` (public) → active plans by `sort`.
  - `POST /orders { deviceId, planIds }` (`@RequireAuth`, rate limit 10 per 10 min per user) → own device, not blocked → `validateOrder` → `Order` (`items` snapshot, `expiresAt = now + 24 h`) → `createPayment` → status `pending`, `redirectUrl` → `{ orderId, redirectUrl }`. Provider down → order `failed`, 503 `PAYMENT_PROVIDER_DOWN`.
  - `GET /orders/:id` (owner) → `OrderView`; `GET /orders` (owner) → list for the profile.
  - `applyPayment(db, deps, providerPaymentId, source: 'webhook' | 'reconcile')` — `getPayment` → `paid` with `amountRub === order.amountRub` and `currency === 'RUB'` → in one transaction `UPDATE "Order" SET status='paid', "paidAt"=now() WHERE id=$1 AND status IN ('created','pending')`; one row updated → entitlements via `nextWindow` per plan, then (after commit) enqueue `apple:registerDevice { deviceId, tier }` when the device is not `active` or its account tier differs, and send `order-paid` («Оплата получена»); zero rows → order already handled (no-op) or closed (`expired|refunded|failed` → critical alert `late_payment:<orderId>`). Mismatch → critical alert `payment_mismatch:<orderId>`, order unchanged. Provider says `failed` → order `failed`.
  - `POST /billing/webhooks/:provider` → `authenticateWebhook` (fail → 401, warning log without body) → insert `PaymentEvent` (unique `eventKey`; conflict → 200 `{ ok: true }`) → `applyPayment` → store `result` → 200. Unexpected errors → 500 so the provider retries; the event row is deleted in that case so the retry is processed.

### Task 5: Billing jobs — reconcile, expire, remind

**Files:**
- Create: `apps/worker/src/billing/{reconcile-orders,expire-orders,expire-rights}.ts`, `apps/worker/src/queues/billing.ts`, `apps/api/src/billing/internal.controller.ts`

- Test: `apps/worker/test/billing-jobs.int.test.ts`

**Interfaces:**
- Consumes: `applyPayment` through an internal API route. Provider adapters and their secrets stay in the API; the worker calls `POST /api/v1/internal/billing/reconcile/:orderId` with header `X-Internal-Token: <INTERNAL_TOKEN>` (32+ random bytes, env of api and worker). The route is reachable only on the compose network: Caddy answers `respond /api/v1/internal/* 404` before the `/api/*` proxy.
- Produces:
  - Job `billing:reconcileOrders` (every 5 min): orders `pending` for more than 10 minutes and not expired → internal reconcile route (which runs `applyPayment(…, 'reconcile')`).
  - Job `billing:expireOrders` (every 15 min): `created|pending` past `expiresAt` → one last reconcile; still unpaid → `expired`.
  - Job `billing:expireRights` (hourly): devices without an active device right and status `active` → `expired`; devices `expired` that regain a right → `active` when still in their account's latest profile, otherwise `registerDevice`. Reminders `right-expiring` at 7 and 1 days (dedupe per right and threshold in Redis for 8 days), `right-expired` once.
