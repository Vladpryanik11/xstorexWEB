# M5 Subscription Purchase Scenarios Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement three complete journeys: first purchase without mandatory sign-in/UDID, purchase or renewal in an existing account, and installation with an existing subscription. Confirmed payment starts access immediately; device connection is independent and can happen later.

**Architecture:** A Subscription belongs to a user and can acquire one device later. Orders snapshot plans and create dated entitlements immediately at provider-confirmed payment. A separate fulfillment process registers assigned devices with Apple without changing subscription dates; one shared access resolver drives the app button and API installation checks.

**Tech Stack:** Existing NestJS/Prisma/PostgreSQL, BullMQ/Redis, Next.js, Zod, Vitest and Playwright; Platega adapter plus a fake provider. No new UI or payment SDK is required.

**Spec:** [main specification](../specs/2026-11-02-xstore-design.md), especially §4.1–4.3, §5 and §6.3; [purchase design, 2026-11-06](../specs/2026-11-06-purchase-and-activation-design.md). The owner's latest rule is payment-time activation, replacing the earlier discussion of activation after Apple readiness. Builds on revised M2 (email identity/provisional recovery), M3 (registration), M4 (signing/install).

## Global Constraints

- All M0–M4 constraints hold. Public catalog and prices require no account. First checkout requires neither an email code nor a UDID before payment.
- Payment: Platega only; RUB, positive whole-ruble prices configured by admin, no seeded commercial price. No automatic recurring charge is introduced.
- One Subscription supports one iPhone/iPad; multiple devices need separate subscriptions. Subscription.deviceId can be null at payment.
- First period and lapsed renewal start at provider-confirmed `paidAt`; device assignment/Apple readiness never start, pause or reset the clock. Early renewals stack after existing periods.
- Before payment show amount, period, one-device scope, immediate start, and possible Apple registration wait of up to 72 hours.
- Provisional checkout account: `isProvisional=true`, `email=null`, checkoutEmail contact. Never log into an existing account by typed email. Recovery requires the M2 email-code proof.
- Unpaid local order lifetime: 24 hours. Unknown provider outcome blocks a replacement payment until reconciled or definitively canceled/failed at the provider.
- Webhooks: POST `/api/v1/billing/webhooks/:provider`, raw body ≤64 KB, Origin-exempt, provider-authenticated, re-read payment/amount/currency from provider before applying. Reconcile every 5 minutes for pending payments older than 10 minutes.
- Rights chain is `(subscriptionId, device)` or `(subscriptionId, addon:<code>)`; null device does not mean null subscription dates.
- Reminders: 7 days and 1 day before subscription expiration. Fulfillment retries never extend rights.

## Review Focus

1. Known email entered by a logged-out visitor must not expose that account → Task 4 `checkout email is not a credential`, Task 7 same public checkout for known/unknown email.
2. Cookie loss or enrollment retry must preserve a paid purchase and its original dates → Tasks 5/7 recovery test.
3. Two simultaneous payment events or binding requests must not duplicate rights or assign two devices → Tasks 1/4 transactional tests.
4. A subscription can expire before device connection; connection must not revive or restart it → Task 2 dates test, Task 9 subscriber branch.
5. Unknown/late provider results must not cause two payable attempts or silently disappear → Tasks 3–5 timeout, local-expiry and late-confirmation tests.

### Task 4: Checkout, immediate access, device assignment and webhooks

**Files:**
- Create: `apps/api/src/billing/{billing.module,plans.controller,orders.controller,subscriptions.controller,webhooks.controller,orders.service,apply-payment}.ts`.
- Modify: `packages/shared/src/client.ts`, `apps/api/src/auth/session.service.ts`, notification job contracts.
- Test: `apps/api/test/{orders,subscriptions,webhooks}.int.test.ts`.

**Interfaces:**
- `GET /billing/plans` is public. `POST /orders {planIds,checkoutKey,checkoutEmail?,subscriptionId?,deviceId?,returnTo?,intent:purchase|renew|addon|new_device}` uses Origin checks/rate limit 10/10min per IP and per existing user. Require at least one active plan; server recomputes total. `safeNext` validates returnTo.
- Before creating any user/subscription, take a transactional advisory lock on global checkoutKey and check its unique Order. A concurrent first request without the owner cookie receives generic 409 CHECKOUT_IN_PROGRESS, no order details, no new User and no new payment. With the owner session, an exact payload replay returns the existing result; another owner/key collision never authorizes access. The browser waits for its first response; a lost cookie is recovered by email code.
- With user session, use only that user and owned subscription/device. Without one, create a provisional account/cookie for this purchase, never resolve identity from typed email. Provisional contact remains fixed after a confirmed purchase. The client generates checkoutKey with crypto.randomUUID once per purchase intent and retains it across retries; the key alone cannot retrieve or authorize the order.
- Existing subscriptionId targets renew/addon; owned device with no subscription creates its one slot; neither id creates an unassigned slot. Server prevents incompatible duplicates and reuses global checkoutKey only for the same normalized payload. Active-base purchase requires an explicit renewal/new-device intent, not an accidental second first purchase.
- `applyPayment(db,deps,providerPaymentId,source)` re-reads provider. Under an order/subscription lock, verify amount/currency and status; first confirmed payment records stable paidAt and creates each dated Entitlement via Task 2, then sets fulfillment awaiting_device or activating/ready. PaymentEvent result and rights commit atomically; repeated events do not shift dates. Unknown/closed-order confirmations create support alerts and remain visible in payment history, without duplicate rights.
- `GET /orders`, `GET /orders/:id`, `GET /subscriptions` are owner-only; no-store. GET of another user's order →404. `POST /subscriptions/:id/device {deviceId}` requires paid non-refunded rights, owned device, no other assigned device/subscription. First assignment writes deviceId/assignedAt and queues fulfillment; same binding is idempotent, another is SUBSCRIPTION_ASSIGNED. Never change entitlement dates.
- Fulfillment starts only while a base right is currently active; if already expired, keep device connection and offer renewal. Registration must match the paid base tier. API sends `apple:registerDevice` only after commit; recovery job can resend safely. When ready, fulfillment becomes ready without changing payment/access dates.
- Unknown payment status prevents a replacement; final provider failure permits a new attempt, preserving subscription target and app. DB transaction/durable retry must handle crash after provider confirmation but before queue/mail dispatch.
