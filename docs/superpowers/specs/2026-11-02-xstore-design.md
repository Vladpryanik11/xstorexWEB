# Xstore (xstorex.ru) — спецификация, этап 1

Дата: 2026-11-02 · Обновлено: 2026-11-05 · Статус: утверждена

## 1. Цель

Xstore — магазин IPA-приложений для iPhone и iPad с установкой прямо из Safari, без компьютера и сторонних приложений. По функциям продукт равен LazyShop, по внешнему виду повторяет визуальный язык diyorde.com. Это полноценный продукт, а не MVP.

Критерии успеха этапа 1:

- пользователь с iPhone входит по UDID, оплачивает регистрацию устройства через Platega и в один клик ставит приложение из каталога;
- пользователь загружает свой IPA и ставит его, подписанный сертификатом сервиса или своим;
- админ загружает IPA через админку, публикует приложения, управляет пулом аккаунтов Apple, тарифами, пользователями и контентом;
- отзыв сертификата Apple обнаруживается и обрабатывается автоматически;
- сайт работает на своём VPS в Docker по HTTPS.

## 2. Ограничения и решения

| Тема | Решение |
|---|---|
| Контент | Только IPA, на распространение которых есть права. У каждого приложения в админке обязательное поле «основание для распространения». Взломанные приложения и «Premium»-моды не публикуются |
| Оплата | Только Platega (СБП, карты РФ, международные карты, крипта — что включено у мерчанта). Telegram Stars не используются нигде |
| Язык | Только русский. Строки пишутся прямо в коде, библиотеки перевода и переключателя языка нет |
| Дизайн | Визуальный язык diyorde.com: токены, сетка, компоненты, шапка. Логотип, иллюстрации, тексты и скриншоты свои, файлы DIYORDE не копируются |
| Подпись | Пул личных аккаунтов Apple Developer, Ad Hoc distribution + wildcard App ID. Enterprise-сертификаты не используются |
| Хостинг | Свой Linux VPS, всё в `docker compose` |

## 3. Архитектура

TypeScript-монорепо на pnpm workspaces и Turborepo, Node.js 24 LTS.

```
xstore/
├─ apps/
│  ├─ web/     Next.js (App Router, SSR): сайт, кабинет, админка /admin
│  ├─ api/     NestJS: REST /api/v1, вебхуки Platega, приём UDID, OTA-манифесты
│  └─ worker/  BullMQ: подпись (zsign), разбор IPA, Apple-синхронизация, OCSP, уборка
├─ packages/
│  ├─ shared/  схемы zod, типы, коды ошибок, типизированный API-клиент
│  ├─ db/      схема Prisma, миграции, сиды
│  └─ ui/      дизайн-токены (CSS custom properties) и React-компоненты
├─ infra/      docker-compose.yml, Caddyfile, Dockerfile'ы, сборка zsign
└─ docs/       спецификации, планы, ADR
```

**Инфраструктура:** PostgreSQL 17, Redis 7 (очереди BullMQ и rate limit), MinIO (оригиналы IPA, загрузки пользователей, подписанные сборки, иконки и скриншоты), Caddy (автоматический HTTPS Let's Encrypt, раздача `xstorex.ru` и `dl.xstorex.ru`).

**Стили:** CSS Modules и глобальные токены в CSS custom properties. Это позволяет переносить измеренные стили DIYORDE один в один.

**Почему так.** Один язык и общие типы для сайта, админки, API и будущего Telegram Mini App. Воркер отделён от API: только он держит закрытые ключи Apple и запускает zsign. Если подпись падает или зависает, сайт и API продолжают работать. Воркеры масштабируются отдельно.

### 3.1 Модули API

| Модуль | Ответственность |
|---|---|
| `auth` | Сессии в httpOnly cookie, роли `user / support / admin`, вход по email-коду, пароль и TOTP для админов |
| `enrollment` | Генерация подписанного `.mobileconfig` (Profile Service), приём ответа iOS, проверка CMS-подписи, выдача сессии |
| `devices` | Устройства пользователя, их статусы, привязка к аккаунту Apple |
| `apple` | Пул аккаунтов, клиент App Store Connect API (Devices, Certificates, Profiles, Bundle IDs), выпуск сертификатов по своему CSR, проверка OCSP |
| `catalog` | Приложения, версии, категории, подборки, поиск, импорт метаданных из iTunes Search API |
| `storage` | MinIO: presigned multipart upload, временные ссылки на скачивание, удаление |
| `signing` | Задачи подписи, кэш подписанных сборок, своя подпись пользователя |
| `install` | Одноразовые токены, OTA-манифесты, ссылки `itms-services://` |
| `billing` | Тарифы, заказы, права со сроком, интерфейс `PaymentProvider` и реализация Platega |
| `content` | Блог, FAQ, страницы поддержки и юридические страницы |
| `notifications` | Письма через SMTP |
| `admin` | CRUD для всех сущностей, дашборд, журнал действий |

## 4. Ключевые сценарии

### 4.1 Вход по UDID (Safari на iPhone/iPad)

1. `/signin` → «Установить профиль». API создаёт `EnrollmentSession` (nonce, срок 15 минут) и отдаёт `.mobileconfig` с `PayloadType = Profile Service`. В профиле указаны `URL = https://xstorex.ru/api/v1/enrollment/callback?s=<nonce>` и `DeviceAttributes = UDID, PRODUCT, VERSION, SERIAL`. Профиль подписан сертификатом домена с полной цепочкой, поэтому iOS показывает «Проверено».
2. Пользователь: Настройки → «Профиль загружен» → Установить. iOS отправляет POST с CMS-подписанным plist.
3. API проверяет подпись, извлекает UDID, находит или создаёт пользователя и устройство. Затем отвечает `301` на `https://xstorex.ru/enroll/done?t=<одноразовый токен>`. Safari открывается, токен меняется на сессию. На устройстве профиль не остаётся.
4. С компьютера вход по почте, а устройство привязывается позже с iPhone. У одного пользователя может быть несколько устройств.
5. Если сессия входа истекла или подпись ответа неверна, показывается понятная ошибка и кнопка «Попробовать снова».

### 4.2 Покупка и регистрация устройства

1. Пользователь выбирает тариф на `/pricing` → `Order` → платёжная страница Platega.
2. Вебхук Platega проверяется по подписи, сумме и валюте. Повторная доставка не обрабатывается дважды (уникальный ключ события). Заказ становится оплаченным, создаётся `Entitlement` со сроком действия.
3. Задача `apple.registerDevice` выбирает аккаунт нужного уровня (`standard` или `reliable`) со свободным слотом в пределах лимита аккаунта. Регистрирует UDID через ASC API и пересоздаёт wildcard Ad Hoc профиль аккаунта (`revision + 1`). Устройство переходит в статус `active`.
4. Если Apple держит устройство в обработке (до 72 часов), статус `processing`. Воркер периодически проверяет его и отправляет письмо, когда устройство активно.
5. Если свободных слотов меньше порога из настроек, админ получает алерт.

### 4.3 Установка из каталога

1. «Установить» на `/app/[slug]` → API проверяет права устройства на приложение.
2. В кэше ищется `SignedBuild` с ключом (версия × аккаунт × ревизия профиля, содержащая устройство). Если его нет, ставится задача `signing.sign`: воркер берёт оригинал из MinIO, подписывает через zsign сертификатом и профилем аккаунта и загружает результат в MinIO.
3. Прогресс передаётся в браузер через SSE, кнопка показывает «Подписываем 45%».
4. Выдаётся `itms-services://?action=download-manifest&url=https://xstorex.ru/api/v1/install/<token>/manifest.plist`. Токен одноразовый, привязан к пользователю и устройству, живёт 1 час. В манифесте временная ссылка на IPA (`dl.xstorex.ru`, 15 минут), иконки 57 и 512 px, `bundle-identifier`, `bundle-version`, `title`.
5. Факт установки пишется в `InstallEvent`.
6. Подписанные сборки удаляются по `lastUsedAt` и при нехватке места.

После заполнения аккаунта (100 устройств) одна подписанная копия приложения обслуживает всех его пользователей.

### 4.4 Загрузка IPA через админку

1. Админ перетаскивает один или несколько IPA (до 10 ГБ каждый) в раздел «Приложения → Загрузить IPA». Файл загружается частями напрямую в MinIO по presigned URL, с прогрессом и докачкой при обрыве.
2. Задача `ipa.inspect` в воркере:
   - читает `Info.plist`: название, bundle id, версия, сборка, `MinimumOSVersion`, `UIDeviceFamily`;
   - извлекает иконку и переводит её из Apple CgBI-PNG в обычный PNG;
   - считает размер и sha256;
   - проверяет шифрование FairPlay (`cryptid` в `LC_ENCRYPTION_INFO`). Зашифрованный IPA помечается как непригодный к подписи, админ видит причину;
   - отбрасывает архивы с некорректной структурой и zip-бомбы.
3. Если bundle id уже есть в каталоге, IPA становится новой версией этого приложения. Если нет — черновиком нового. Метаданные (описание, скриншоты, категория, разработчик) подтягиваются из iTunes Search API, админ правит их и публикует.
4. Публикация новой версии сбрасывает «последнюю версию» в каталоге. Старые версии остаются доступными в истории.

### 4.5 Своя подпись (Signer)

1. На `/signer` пользователь с опцией `signer` загружает IPA так же, частями. Лимит размера задан тарифом.
2. `ipa.inspect` работает как в 4.4, зашифрованные IPA отклоняются с объяснением.
3. Подпись выполняется сертификатом аккаунта Xstore, к которому привязано устройство, или своим `.p12` + `.mobileprovision` пользователя (`UserCertificate`, хранится зашифрованным). Для своего сертификата проверяется, что UDID есть в профиле и сертификат не истёк.
4. Опции: другой bundle id и другое название, чтобы поставить дубль.
5. Установка как в 4.3. Загрузки пользователя удаляются через срок из настроек.

### 4.6 Отзыв сертификата и блокировка аккаунта

1. Воркер раз в 10 минут проверяет OCSP всех активных сертификатов.
2. При отзыве:
   - аккаунт помечается;
   - создаётся новый ключ и CSR, через ASC API выпускается сертификат;
   - пересоздаётся профиль, кэш `SignedBuild` аккаунта сбрасывается;
   - пользователи аккаунта получают письмо «переустановите приложения».
3. При блокировке аккаунта целиком (ошибки авторизации ASC, членство не активно) админ получает список затронутых устройств и предложение переноса на свободные аккаунты по гарантии тарифа (`warrantyDays`). Перенос подтверждает админ.
4. За 30 дней до окончания членства аккаунта админу приходит предупреждение.

## 5. Модель данных (Prisma, PostgreSQL)

**Пользователи**
- `User`: id, email (уникальный, необязательный), role, passwordHash и totpSecret (только для staff), createdAt.
- `Session`: id (SHA-256 токена из cookie), userId, kind (`user | staff`), deviceId (устройство, с которого выполнен вход по UDID), expiresAt, ip, userAgent, lastSeenAt.
- `EnrollmentSession`: nonce, status, userId (при привязке устройства к уже вошедшему пользователю), deviceId, next, expiresAt.
- `Device`: id, userId, udid (уникальный), product, iosVersion, name, status (`new | pending | processing | active | blocked | expired`), appleAccountId, ascDeviceId, includedInRevision (первая ревизия профиля аккаунта, в которую попало устройство), tierWanted, registeredAt.

**Apple**
- `AppleAccount`: id, title, teamId, tier (`standard | reliable`), status (`active | auth_error | blocked`), membershipExpiresAt (вводит админ, ASC API её не отдаёт), deviceLimit (≤ 100, отдельно для каждого класса устройств), usedIphoneSlots, usedIpadSlots, ascKeyId, ascIssuerId, ascPrivateKeyEnc, wildcardBundleAscId, lastRevokedAt.
- `AppleCertificate`: id, accountId, ascCertificateId, serial, p12Enc, p12PasswordEnc, expiresAt, status (`active | rotated | revoked | expired`), ocspStatus, checkedAt, lastGoodCheckAt.
- `ProvisioningProfile`: id, accountId, revision, ascProfileId, certificateId, profileBlob, udids[], expiresAt.

**Каталог**
- `App`: id, slug, name, subtitle, description, developer, categoryId, iconKey, screenshotKeys[], bannerKey, removedFromAppStore, rightsBasis, accessLevel (`free | addon:<code>`), status (`draft | published | hidden`), hiddenReason, rating, ratingCount (из iTunes, для подборки «Самый рейтинговый»), languages[], itunesId, timestamps.
- `AppVersion`: id, appId, version, build, bundleId, minIos, sizeBytes, sha256, ipaKey, icon57Key, encrypted, changelog, status, publishedAt. Сочетание bundleId × version × build уникально.
- `Category`: slug, name, icon, sort.
- `Collection` + `CollectionItem`: slug, title, layout (`grid3 | icons | screenshots | banner`), source (`manual | top_downloads | trending | top_rated | recently_updated`), sort, limit, onHome; у элемента подборки position и pinned.

**Загрузки**
- `IpaUpload`: id, ownerId, purpose (`catalog | signer`), bucket, key, s3UploadId, fileName, sizeBytes, partSize, status (`uploading | uploaded | inspecting | ready | rejected | expired`), rejectCode, inspect (результат `ipa.inspect`), appVersionId, expiresAt. Отслеживает загрузку частями с докачкой и в админке, и в Signer.

**Подпись и установка**
- `UserUpload`: id, userId, uploadId (→ `IpaUpload`), разобранные метаданные (name, bundleId, version, build), sizeBytes, iconKey, expiresAt.
- `UserCertificate`: id, userId, title, teamId, certSerial, p12Enc, passwordEnc, profileBlob, profileName, appIdPattern, udids[], expiresAt.
- `SigningJob`: id, userId, deviceId, source (appVersion или userUpload), certificate source, options, queueJobId, status, progress, errorCode, signedBuildId.
- `SignedBuild`: id, sourceKey, accountId, certificateId, profileRevision, ipaKey, sizeBytes, createdAt, lastUsedAt.
- `InstallToken`: token (хранится SHA-256), userId, deviceId, signedBuildId или buildKey (сборка Signer), данные для манифеста (title, bundleId, bundleVersion, иконки), expiresAt, usedAt, usedIp, usedUa.
- `InstallEvent`: appId, deviceId, createdAt.

**Оплата**
- `Plan`: id, code, title, kind (`device | addon`), tier, durationDays, priceRub, features (JSON: `signer`, `uploadLimitMb`, `warrantyDays`), active, sort. Доступ к платным наборам задаётся только через `App.accessLevel = addon:<Plan.code>`.
- `Order`: id, userId, deviceId, planIds, items (состав и цены на момент заказа), amountRub, status (`created | pending | paid | failed | expired | refunded`), provider, providerPaymentId, redirectUrl, paidAt, expiresAt.
- `PaymentEvent`: id, provider, eventKey (уникальный), payload, result, processedAt.
- `Entitlement`: id, deviceId, planId, planCode, kind, startsAt, expiresAt, orderId, grantedById (ручная выдача), revokedAt.

**Контент и сервис**
- `Article`, `FaqItem`, `Page`.
- `AuditLog`: actorId, action, entity, entityId, diff, ip, createdAt.
- `Alert`: kind, severity (`info | warning | critical`), title, details, dedupeKey (уникальный), createdAt, resolvedAt. Алерты админу: мало слотов, ошибки ASC, отзыв сертификата, конец членства, сбои подписи, оплаты и бэкапов.
- `NotificationLog`: template, to, subject, status, error, createdAt.
- `Setting`: ключ–значение для порогов и лимитов.

Правила:
- Права привязаны к устройству. Второе устройство оплачивается отдельно.
- Поля с суффиксом `Enc` шифруются AES-256-GCM мастер-ключом из переменной окружения, с версией ключа для ротации. Расшифровывают их только модуль `apple` и воркер. Админка позволяет заменить секрет, но не показывает его.
- «Самый загружаемый» считается по `InstallEvent` за 30 дней, «Тенденции» — по приросту за 7 дней. Порядок в подборке админ может закрепить вручную.

## 6. Интерфейс

### 6.1 Визуальный язык

Источник — diyorde.com. Точные токены и правила лежат в проектном скилле `.claude/skills/xstore-design/SKILL.md`. Кратко:

- Шапка: градиент `#0C45B7 → #134CBE 30% → #1C55C8 51% → #245DD0 69% → #3B75E9`, высота 60px, sticky. На главной шапка прозрачная поверх героя и заливается градиентом при прокрутке.
- Шрифт `"Helvetica Neue", Helvetica, Inter, Arial, sans-serif`. Ряды каталога используют системный шрифт `-apple-system`.
- Синий `#1A6EEA`, ink `#062260`, фон страницы `#F3F4F6`, поверхность `#F0F3FA`, радиус карточек 1.5rem.
- Компоненты: кнопка-пилюля `rd-btn`, стеклянный поиск, горизонтальные рельсы со snap, ряды 3×N, ряд иконок, чипы категорий, карточки-обложки 16:10, плавающая плашка установки, боковое меню на мобильных, футер.

### 6.2 Шапка (должна совпадать в точности)

Эталон авторизованной шапки: `docs/superpowers/specs/assets/header-logged-in.png`.

| Состояние | Слева | Центр | Справа |
|---|---|---|---|
| Гость | логотип Xstore 38×38, радиус 10px | «Блог» · «Вопросы» · «Поддержка» | пилюля «Установить» + приглушённое «Войти» |
| Авторизован | логотип Xstore | «Ваши устройства» · «Профиль» · «Блог» · «Вопросы» · «Поддержка» | приглушённое «Выйти» |

- Пункт меню: 14px/500, цвет `#E6EDFB`, высота 34px, отступы 0 12px, пилюля. Активный пункт (`aria-current="page"`) — фон `rgba(255,255,255,.2)`, при наведении `rgba(255,255,255,.14)`.
- «Войти» и «Выйти»: `rgba(230,237,251,.72)`, при наведении белый.
- «Установить»: пилюля 40px, фон `rgba(255,255,255,.2)` с внутренними бликами.
- На ширине меньше 768px пункты меню прячутся в бургер, который открывает боковое меню во весь экран (фон `#F0F3FA`, иконки `#1A6EEA`).
- Переключателя языка нет.

### 6.3 Страницы

**Публичные**
- `/` — главная. Герой с заголовком и поиском, карусель баннеров, затем подборки из админки: «Самый загружаемый» (сетка 3×N), «Тенденции» (иконки), чипы категорий, «Самый рейтинговый», «Удалённые из App Store» (со скриншотами), «Недавно обновлено», блок блога. Внизу плавающая плашка «Xstore — Установить».
- `/app/[slug]` — иконка, название, подзаголовок, кнопка состояния («Войти» → «Купить» → «Подписываем N%» → «Установить» → «Открыть инструкцию»), полоса фактов (категория, разработчик, язык, размер, версия), скриншоты, описание с «ещё», блок «Информация», история версий.
- `/category/[slug]`, `/list/[slug]`, `/search`.
- `/signin` — вход через профиль с пошаговой инструкцией и картинками iOS; ссылка «Войти по почте».
- `/enroll/done` — завершение входа.
- `/install` — добавление Xstore на домашний экран (web clip + PWA manifest).
- `/pricing`, `/checkout/[orderId]`.
- `/blog`, `/blog/[slug]`, `/faq`, `/support`, `/terms`, `/privacy`.

**Кабинет**
- `/devices` — «Ваши устройства»: карточка устройства со статусом в Apple, правами и сроками, кнопками «Продлить» и «Подписать свой IPA», историей установок.
- `/profile` — «Профиль»: email для уведомлений, заказы, активные сессии, выход.
- `/signer` — свои IPA и свои сертификаты, подпись и установка.

**Админка `/admin`** — плотнее, с таблицами, на тех же токенах:
- дашборд: выручка, новые устройства, свободные слоты, очереди, отозванные сертификаты, ошибки подписи;

## 7. Безопасность

- HTTPS везде, HSTS. Cookies `HttpOnly; Secure; SameSite=Lax`. На изменяющих запросах проверяется `Origin`.
- Админка: пароль (argon2id) и обязательный TOTP. Гарды ролей на каждом эндпоинте, все изменения пишутся в `AuditLog`.
- Rate limit через Redis на вход, коды, enrollment, подпись и загрузки.
- Вебхуки Platega: проверка подписи, суммы и валюты, идемпотентность по `PaymentEvent.eventKey`. Раз в 5 минут зависшие заказы сверяются с API Platega.
- Секреты шифруются, как описано в разделе 5, и никогда не пишутся в логи.
- Токены установки одноразовые, ссылки MinIO живут 15 минут.
- Загрузки IPA проверяются на размер, структуру и коэффициент сжатия. zsign запускается во временной директории с таймаутом и лимитами CPU и памяти.
- Пользовательский Markdown санитизируется.
- Условия использования запрещают загружать IPA без прав. В админке есть процедура скрытия по жалобе.

## 8. Ошибки и наблюдаемость

- Единый формат ошибок API: `{ code, message }`, коды в `packages/shared`. Пользователь видит понятный текст на русском.
- Задачи BullMQ повторяются с экспоненциальной паузой. Неудачные попадают в отдельную очередь и видны в админке, с кнопкой «Повторить».
- Ошибки ASC API разделяются по типам:
  - нет слотов → следующий аккаунт;
  - 401/403 → аккаунт помечается и уходит алерт;
  - 429 → пауза и повтор.
- Логи в JSON (pino) с request id, healthcheck-эндпоинты у каждого сервиса, хук для внешнего трекера ошибок через переменную окружения.

## 9. Тестирование

Работа ведётся по TDD.

- **Модульные (Vitest):**
  - расчёт прав и сроков;
  - выбор аккаунта Apple;
  - генерация `.mobileconfig` и манифеста;
  - разбор ответа iOS по записанным примерам;
  - разбор `Info.plist`, конвертация CgBI, проверка `cryptid`;
  - подпись вебхука Platega.
- **Интеграционные:** API на реальных PostgreSQL, Redis и MinIO в Docker. ASC API и Platega подменяются моками на записанных ответах.
- **Подпись:** настоящий zsign в контейнере воркера на тестовом IPA, собранном для тестов; проверяется структура подписи.
- **E2E (Playwright, WebKit, эмуляция iPhone):** вход через симуляцию ответа iOS, покупка через мок Platega, получение ссылки установки, загрузка IPA в админке. Отдельный прогон сравнивает шапку с эталоном (`header-logged-in.png`).
- **Перед релизом:** ручная проверка на реальном iPhone — установка профиля, OTA-установка, работа приложения.

## 10. Деплой

- `docker compose` на VPS: caddy, web, api, worker (несколько реплик), postgres, redis, minio.
- Ежедневный `pg_dump` и зеркалирование bucket'а оригиналов IPA на внешний диск или второй VPS.
- GitHub Actions: lint, typecheck, тесты, сборка образов, деплой по SSH с миграциями Prisma.
- Локальная разработка на Windows: Node.js нативно, PostgreSQL/Redis/MinIO/воркер — в Docker Desktop.

## 12. Известные ограничения

- Wildcard-профиль не даёт entitlements для push-уведомлений, iCloud и App Groups. В переподписанных приложениях эти функции не работают (как у LazyShop). Явные App ID — этап 3.
- Apple позволяет 100 iPhone на аккаунт за год членства. Удалённое устройство освобождает слот только после продления.
- IPA, зашифрованные FairPlay, подписать нельзя.
