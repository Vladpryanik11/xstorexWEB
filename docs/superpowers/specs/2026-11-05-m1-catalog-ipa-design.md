# Xstore — M1: каталог, административная загрузка IPA и публичная витрина

**Статус:** проект спецификации; первые два изолированных технических инкремента начаты по команде владельца, решения R1–R5 требуют отдельного утверждения.  
**Основание:** `main` @ `7d274a95d4c61a0014c73c1b8313f471f9eb8669` (проверено 05.11.2026); `CLAUDE.md`; `docs/superpowers/specs/2026-11-02-xstore-design.md`, §§ 3.1, 4.4, 5–9, 11; `.claude/skills/xstore-design/SKILL.md`.  
**Область:** только M1, без M2–M7, кроме явно согласованных блокирующих зависимостей.

## 1. Результат и границы

Пользователь на русском языке видит рабочую главную страницу, категории, подборки, поиск и карточку приложения. Контент поступает из PostgreSQL и доступен лишь после ручной публикации. Администратор может безопасно загрузить законно распространяемый IPA объёмом до 10 ГБ по частям в MinIO, увидеть результат `ipa.inspect`, дополнить метаданные, указать **обязательное основание для распространения**, опубликовать, скрыть и управлять версиями, категориями и подборками.

**Входит:** модели `App`, `AppVersion`, `Category`, `Collection`, `CollectionItem`; storage abstraction и presigned multipart upload; инспекция IPA; iTunes Search API как источник черновых метаданных; CRUD каталога; русские публичные страницы `/`, `/app/[slug]`, `/category/[slug]`, `/list/[slug]`, `/search`; unit/integration/E2E-проверки.

**Не входит:** вход по UDID/email и кабинет M2, пул Apple Developer M3, серверная подпись и фактическая OTA-установка M4, Platega M5, Signer M6, блог/SEO/production M7. Кнопка установки на M1 не выдаёт нерабочий OTA-URL и не имитирует действующую подписку; её поведение до M4 указывается явно и на русском.

## 2. Данные и публикация

- `Category`: `id`, `slug` (unique), `name`, `icon`, `sort`; связь с `App`.
- `App`: `id`, `slug` (unique), `name`, `subtitle`, `description`, `developer`, `categoryId`, `iconKey`, `screenshotKeys[]`, `removedFromAppStore`, `rightsBasis`, `accessLevel`, `status` (`draft | published | hidden`), `createdAt`, `updatedAt`.
- `AppVersion`: `id`, `appId`, `version`, `build`, `bundleId`, `minIos`, `sizeBytes` (BigInt), `sha256`, `ipaKey`, `encrypted`, `changelog`, `status` (`draft | published | hidden`), `publishedAt`; дополнительные извлечённые данные `deviceFamilies` и диагностический `inspectionErrorCode` — **на согласование**, т. к. не перечислены в исходной модели.
- `Collection`: `id`, `slug` (unique), `title`, `layout` (`grid3 | icons | screenshots | banner`), `source` (`manual | top_downloads | trending | top_rated | recently_updated`), `sort`.
- `CollectionItem`: `collectionId`, `appId`, `sort` (порядок вручную закреплённых приложений); уникальность пары. Способ сочетания динамических результатов и закреплений требуется утвердить до реализации.
- Техническая сущность `CatalogUpload` для управления multipart, докачкой, TTL, владельцем операции, `uploadId`, частями и статусом — **предложение для согласования**, поскольку оригинальная спецификация не перечисляет её отдельно; альтернативой является Redis со сроком жизни, но после сбоя возобновление менее надёжно.

### Инварианты

1. `rightsBasis` обязателен для публикации и должен содержать конкретное правовое основание (владелец прав/лицензия/разрешение). API запрещает публикацию с пустым или состоящим из пробелов значением. Запрещены взломанные и Premium-модифицированные сборки.
2. Публичный каталог читает лишь `App.status=published` с хотя бы одной опубликованной версией, успешно прошедшей проверку и `encrypted=false`; `hidden` и `draft` не выдаются в поиске, списках, подборках и карточках.
3. Для одного приложения последняя опубликованная версия выбирается детерминированно по дате публикации с вторичным ключом `id`; прежние версии остаются в истории. Уникальность идентификации версии по `appId + bundleId + version + build` и стратегия конфликтов утверждаются перед миграцией.
4. Удаление категории с приложениями, подборки с элементами, версии с IPA, на который могут ссылаться будущие подписанные сборки, не должно вызывать потерю данных: по умолчанию soft-hide/запрет удаления; очистка объектов MinIO отделена от скрытия записи.
5. `accessLevel` — совместимое с M5 текстовое значение `free` или `addon:<code>`; M1 не рассчитывает права, не открывает платный контент и не подделывает наличие `Entitlement`.
6. Внешние метаданные iTunes — подсказка для редактирования, **не подтверждение права** распространять IPA и изображения. Никогда не перезаписывать вручную подтверждённые поля без явного выбора администратора.

## 3. Загрузка и проверка IPA

### 3.1 Storage abstraction

В API слой `storage` с S3-совместимым адаптером MinIO: создать multipart-сессию, выдать ограниченные по сроку presigned URL для отдельных частей, перечислить загруженные части, завершить сборку, прервать, открыть поток на чтение, создать временную ссылку на объект, удалить объект. Все ключи генерируются сервером, строго из разрешённого namespace; клиент не может произвольно задавать bucket/key. Креденшелы и внутренний адрес MinIO не оказываются в ответе API (кроме адреса presigned-запроса, доступного клиенту). Клиентский браузер загружает части напрямую в MinIO с разрешённым CORS и получает ETag; затем подтверждает завершение через API.

Лимит **до 10 ГБ на IPA**, ограничение размера частей и параллелизма, TTL сессии, максимальное число частей и cleanup — конфигурируемые, значения зафиксировать в плане и тестах. Поддерживаются прогресс и возобновление после разрыва, сверка неполных частей, отмена и уборка брошенных сессий. Не считать файл безопасным по расширению или заголовку `Content-Type`.

### 3.2 `ipa.inspect` (BullMQ, worker)

- Задача ставится **после подтверждённого завершения** multipart; идемпотентна по `CatalogUpload.id` / идентификатору версии; ретраи с backoff, ошибки видны в админке без секретов.
- Читать IPA потоково, валидировать ZIP, `Payload/<AppName>.app/Info.plist`, запрещать traversal (`../`, абсолютные пути), symlink escape, повторяющиеся пути, подозрительные сжатия, огромные entry и превышение общего лимита распаковки. Лимиты на число файлов, распакованный размер и ratio — отдельные параметры с негативными тестами; при превышении прекращать обработку.
- Получать `CFBundleIdentifier`, `CFBundleShortVersionString`, `CFBundleVersion`, `MinimumOSVersion`, `UIDeviceFamily`; валидировать форматы и записывать диагностические причины, а не оставлять частично опубликованную запись.
- Извлечь подходящую иконку из набора AppIcon; декодировать Apple CgBI-PNG в обычный PNG, сохранив отдельно в MinIO; предусмотреть fallback на ручную иконку.
- Считать действительный `sizeBytes` и потоковый SHA-256 **полного загруженного IPA**, сверять с результатом завершённой сборки.
- Проверять Mach-O `LC_ENCRYPTION_INFO` и `LC_ENCRYPTION_INFO_64`, в том числе universal/fat бинарники; если какой-либо исполняемый slice имеет `cryptid > 0`, `encrypted=true`, подпись и публикация недоступны, причина показывается администратору.
- При ошибке архив не становится публичным; объект помещается в карантин/отмечается для безопасной очистки согласно TTL. Не запускать исполняемые файлы из IPA.

## 4. Каталог API и страницы

**Публичные read-only маршруты** (конкретные URL и DTO закрепить в плане): получение главной (публичные подборки), списка категорий, подборки, приложения с опубликованными версиями, поиска и списка по категории. Пагинация, нормализация запроса, bounded limit, защита от тяжёлых запросов и сортировка стабильны. Запросы не открывают поля `rightsBasis` целиком, внутренние MinIO keys, диагностические ошибки инспекции и черновики.

**Административные маршруты**: загрузка/докачка/отмена, просмотр состояния инспекции, CRUD категорий/приложений/подборок/версий, ручной импорт метаданных iTunes, предварительный просмотр и публикация/скрытие. Каждая мутация требует надёжной admin-аутентификации и авторизации, защиты от CSRF/подмены Origin и аудита действий. Открытые `/admin` или `/api/v1/admin/*` без такого контроля запрещены.

**Страницы:** `/` — реальный герой, поиск, баннеры, «Самый загружаемый», «Тенденции», категории, рейтинговые, удалённые из App Store, недавно обновлённые; `/app/[slug]` — иконка, описание, факты, скриншоты, версии; `/category/[slug]`, `/list/[slug]`, `/search` — SSR и осмысленные пустые состояния; административная область каталога `/admin/apps`, `/admin/apps/upload`, формы категорий/подборок. Визуал строго по `.claude/skills/xstore-design/SKILL.md`: mobile-first 390/768/1280, токены, доступность focus-visible и reduced-motion, без файлов DIYORDE.

**Динамические подборки:** `recently_updated` можно вычислять по версии; `top_downloads` / `trending` требуют `InstallEvent` M4, `top_rated` — ещё не описанного источника рейтинга. До появления источников допускается только явно задокументированное пустое состояние или ручное наполнение, **без вымышленных счётчиков и оценок**. Для блога на главной M1 — честное пустое состояние до M7.

## 5. Открытые архитектурные решения — блокируют написание кода

**R1 (критическое). Аутентификация админки до M2.** В основном плане админка каталога должна работать уже на M1, а полноценные сессии и роли отнесены к M2. Предлагаемый безопасный вариант: выделить минимальный совместимый с будущим `auth` staff-контур (пароль `argon2id`, обязательный TOTP, secure httpOnly session, role guard, Origin/CSRF) и минимальный `AuditLog` уже в M1, с последующим расширением в M2/M7. Это **изменение очерёдности**, оно требует явного утверждения владельца. Если его не утверждать, маршруты админки должны оставаться закрытыми до M2, и M1 нельзя считать полностью завершённой.

**R2.** Разрешить ли техническую `CatalogUpload` (PostgreSQL) для восстановления multipart, лимитов и уборки; альтернативный Redis TTL.

**R3.** Уточнить правило версии/дубликата для одного bundleId, соотношение `App.status` и `AppVersion.status`, критерии изменения опубликованной версии.

**R4.** Уточнить пороговые значения инспектора (коэффициент сжатия/размер распаковки/число файлов), сроки хранения неудачных загрузок и размер части; значения зафиксировать тестами до реализации.

**R5.** Динамические подборки без `InstallEvent` и оценок: временно пустые + ручные закрепления или сдвиг дополнительных сущностей в M1.

Ни одно решение не реализуется молча; сначала согласовать эту спецификацию и отдельный план M1 согласно `CLAUDE.md`.

## 6. Приёмка M1

- [ ] Подтверждены решения R1–R5, статус спецификации — «утверждена».
- [ ] Prisma migration поднимается на пустой и существующей M0-БД; инварианты публикации и уникальности покрыты тестами.
- [ ] IPA до 10 ГБ отправляется непосредственно в MinIO через multipart с прогрессом, возобновлением и отменой; retry/cleanup покрыты интеграционными тестами.
- [ ] Фикстуры: валидный IPA, malformed ZIP, zip-bomb, traversal/symlink, CgBI-PNG, FairPlay cryptid и fat Mach-O; тесты подтверждают корректное поведение.
- [ ] Администратор может безопасно обработать IPA и вручную опубликовать/скрыть приложение; без `rightsBasis` или с FairPlay публикация невозможна.
- [ ] Публичные страницы SSR показывают только опубликованный контент, поиск и фильтры работают; пустые состояния корректны; нет ложной работающей установки.
- [ ] Успешные unit, интеграционные (PostgreSQL/Redis/MinIO), E2E и проверки мобильной/десктопной вёрстки.
- [ ] Выполнены `pnpm lint && pnpm typecheck && pnpm test && pnpm test:int && pnpm test:e2e && pnpm build` + при завершении вехи code review. До запуска команд ни один пункт не отмечается завершённым.

## 7. Оценка статуса на момент подготовки

Исходный `main`: в Prisma только `Setting`; worker обрабатывает только `system.ping`; публичная главная — заглушка. Отдельного утверждённого плана/спецификации M1 в репозитории нет. Все требования этого файла — проект для утверждения, **не реализованные функции**.
